但**将来 15P/21P 建档后必然还会出现这种重复** —— 靠品名认货就分不清了。

⭐ **再加一道数据库层的防线（2026-11-16 已落地）**：
`uk_product_name_spec` = `UNIQUE(product_name, COALESCE(specification, ''))`
- 精确重复 / **规格留空重复**（普通 UNIQUE 拦不住的那类）→ 建档时直接被拒
- ⚠️ **空格不参与该唯一键** —— 业务要求空格原样保留，
  `'A1.5米 200g'` 与 `'A1.5米200g'` 允许并存为两个 SKU
- 引擎侧靠「L1 原始精确优先 + 归一键歧义作废」保证并存时不串货（宁可漏配不可错配）
- 报错走 `ProductConflictError` → API 返回 **400 + 中文提示**（不是 500 + sqlite 原文）

**两道防线分工**：数据库拦「精确重复 + 规格留空重复」，引擎兜「只差空格的变体并存」。
→ **每次建完档，仍然要跑 `python tools/_verify_match_precision.py`**（它查的是归一后的撞车，索引管不到那类）。

| **盘点单的「审核态」（草稿→审核→入账）** | ⭐ **登记为「明确不做（V1）」** —— 主流有这一道（用友/金蝶都有），但单人使用不需要；文档写明省掉，免得将来多人化时以为漏了 |

### ⚠️ 阶段 1.5 踩到的坑（写进代码注释，别改）
1. ⚠️ **ALTER 加列必须排在 CREATE INDEX 之前** ——
   存量表还没有 `occurred_at` 列时，`CREATE INDEX ... ON stock_ledger(occurred_at)`
   直接报 `no such column: occurred_at` → **整个 `init_db()` 崩掉 → Flask 起不来**（服务直接挂）。
   顺序：CREATE TABLE → **ALTER 补列** → CREATE INDEX → CREATE TRIGGER。
2. ⚠️ **`INSERT OR REPLACE` 绕得过 DELETE 触发器**（`recursive_triggers=0` 时）→
   能无声把流水数量从 10 改成 999 → **第 3 条触发器不能省**，幂等必须「先查后写」。
3. ⚠️ **触发器体的白名单扫描要剥掉字符串字面量** ——
   否则报错文案里的字会被当成写关键字误判。
4. ⚠️ **ALTER 加的列只能追加到表末尾 → 存量库列顺序与文档 CREATE 语句不一致**（无害）
   存量库：`stock_ledger` = `... memo, created_at, occurred_at, balance_after, unit_cost, amount`；
   `stock_counts` = `... created_at, closed_at, as_of`。
   **新建库**（CREATE TABLE 直接建）则与上游 §3.3 / §3.7 **逐字一致**。
   → SQLite 没有「在指定位置插列」的语法，这是 ALTER 的固有限制。
   **列顺序不影响任何行为**（`SELECT *` 的返回顺序会不同，模板里没用 `SELECT *` 展开这 7 张表）。
   ⇒ 体检脚本**不校验列顺序**，只校验列名 / 类型 / NOT NULL / DEFAULT。

### ⚠️ 阶段 1.5 顺带定下的口径（阶段 3 / 5 直接用）
- **`--apply` 只重算 `product_stock.quantity`（缓存），绝不改历史流水** ——
  流水是真值源、缓存是派生值；A3 触发器也不允许改流水。链断 / `occurred_at` 为空 → **只报告不可修**。
- **`occurred_at`（日期）与 `as_of`（时刻）不能直接比大小** —— 阶段 5 提交时按
  `occurred_at > date(as_of)` 切「期间变动」，**同日**流水用 `created_at > as_of` 判定。
- **成本两列已落 DDL，`unit_cost` 记「每个 `product.base_unit` 的成本」**；成本核算方法 V2 再定。

### ⚠️ 重建表要过 4 道坎（写进代码注释，别改）
1. `PRAGMA foreign_keys` **在事务内是 no-op** → 必须先 `conn.commit()` 再关 PRAGMA
2. DROP 一个还被别的表引用的父表 → 必须 `PRAGMA legacy_alter_table=ON`，否则 RENAME 时 SQLite 重解析整个 schema 遇悬空 FK 直接报错

### 本阶段的三个实现决定（与上游文档的补正）

1. **A2 改造形态选 ①**（模型方法统一加 `conn=None`），不选 ②（独立 `posting_service.py` 直写 SQL）。

2. **`not_tracking` 不进 `stock_posting_skips`**。
   `stock_posting_skips` 是「**没入账**的待处理清单」；而 `not_tracking` 的行**已经入账了**
   （流水照记、内部累计照加，只是对外显示 0）→ 放进 skips 会让「未入账行数」虚高，
   也会让「补过账」逻辑误把它当成待补的行。DDL 里保留 `not_tracking` 这个 reason_code 作为预留。
3. **冲销过的行不能再正向过账** —— 这是上游 §4.2「已冲销的行不再允许再次正向过账(UNIQUE(uniq_key) 约束挡住)」的直接落地：

### ⭐ 阶段 3 顺带修掉的回归：`init_db()` 的写事务边界

> 这是阶段 3 引入的**真实生产缺陷**，在全量回归里以「比基线多 2 条 ERROR」的形式暴露出来，已修。

**现象**：全量回归比阶段 2 基线多 2 条 ERROR（`tests/test_voice_api.py` 两条，sqlite3 报错）。
单跑该文件 100% 通过 → 典型的「只在全量套件上下文里炸」。

**根因链**（三层叠加）：

1. **阶段 3 在 `init_db()` 里加了第一条 DML** ——
   `INSERT OR IGNORE INTO warehouses (code='FR')`。
   在**稳定库**上，`init_db()` 此前只有 DDL（`CREATE TABLE IF NOT EXISTS` 全是 no-op）
   和一次性迁移（`if 'xxx' not in cols` 守卫，稳态不跑）→ **一次写都没做过**。
2. **Python sqlite3 的隐式事务** —— `isolation_level=''`（默认）下 DML 会自动开事务，
   且**在显式 commit 之前不结束**。于是那条种子 INSERT 打开的写事务，
   **一路带到了 `init_db()` 的最后一行** → 整个启动过程（几百行 DDL）都占着 SQLite **写锁**。
3. **`conn.close()` 不在 `try/finally` 里** —— `init_db()` 中途抛异常时，
   连接连同未提交的事务一起泄漏 → **写锁被永久持有** → 之后所有写库都报 `database is locked`。

**为什么以前不炸**：阶段 3 之前 `init_db()` 不写库 → 它从来不是锁竞争的受害者。
`tests/test_voice_api.py` 的 autouse fixture 里本来就有一句
`except sqlite3.OperationalError: pass`（作者自己注释「用 try/except 兜底预存锁问题」），
把锁错误静默吞掉了 → 竞争一直存在、一直被吞掉、一直没变成 ERROR。
阶段 3 让 `init_db()` 也变成了受害者 → 原本被吞掉的竞争，炸在 `init_db()` 里 → 测试 ERROR。

**修法**（`models/_init.py`）：
- `init_db()` 拆成**薄壳 + `_init_db_impl(conn)`**：壳里 `try/except/finally`
  保证**异常也走 rollback + close** → 写锁一定还回去；
- 种子 INSERT 之后**立刻 `conn.commit()`** → 写锁窗口从「整个 init_db」缩到「这一条语句」；
- 种子 INSERT 包 `try/except sqlite3.OperationalError` → 被别人占锁时**不让整个应用起不来**
  （`OR IGNORE` + 行本来就存在，失败无害，下次启动再补）。

**回归测试**（`tests/test_stock_posting.py` +2 条）：
- `test_init_db_closes_connection_when_it_raises` —— init_db 抛异常后连接必须已关闭
- `test_init_db_does_not_hold_write_lock_after_return` —— init_db 返回后别的连接必须**立刻**拿到写锁

> ⚠️ **给后续阶段的通用教训**：`init_db()` 里**加任何一条 DML**，
> 都会让「启动即写库」变成常态 → 写锁窗口从 0 变成「整段 init_db」。
> 以后往 `init_db()` 加 DML，**必须紧跟一个 `conn.commit()`**。

### ⭐ 盘点 vs 归零的语义（别搞混）
| | 含义 | 写什么流水 |
|---|---|---|
| **盘点** | 「对齐」—— 实盘数就是真值，账面对不上就调 | 差额≠0 → `adjust` |
| **归零** | 「这批货没了/清仓」→ 盘点时填 0 | `adjust`（调到 0） |

### ⚠️ 本阶段踩到的 3 个坑（写进代码注释，别改）
1. **`[hidden]` 会被作者样式盖掉** —— `<label class="m-field" hidden>` 里的分类 / 搜索词字段

## 三、跨阶段硬约束

| 约束 | 说明 |
|---|---|
| **幂等粒度 = 明细行级** | 同一 `record_id` 只入账一次，靠 `stock_ledger.uniq_key` |
| **红字冲销，不删不改** | 用友/金蝶/SAP 的通用做法：已记账凭证不可删改，错了走红字冲销 |
| **启用只由盘点 / 归零触发** | 过账**绝不**自动启用；未启用时流水照记、对外显示 0 |
| **盘点值天然包含未启用期间的货** | 所以盘点**不需要**「补过账」这个动作，也不重复计算 |
| **改库前 WAL 在线备份** | `D:\BAK\worklog_<stamp>.db`，沿用 `tools/_insert_*_from_image.py` 的安全链：清单 → 算术自检 → 唯一性 → WAL 备份 → FK=OFF 单事务 → 逐字段读回 → 独立进程复核 |
| **数字必须带测量时点** | 库是活的，product 已从 1479 涨到 1543 行，入库明细 1160 → 1162 |
| ⭐ **A1 余额可重算** | `product_stock.quantity ≡ SUM(stock_ledger.quantity)`（**容差 `1e-6`，禁止 `== 0`**）；每条流水记 `balance_after`；每阶段收尾跑 `verify_stock_balance.py` |
| ⭐ **A2 单一事务** | 过账 / 冲销 / 盘点提交 / 归零走**单一连接**的 `BEGIN IMMEDIATE`；`models/inventory.py` 不得自行 commit |
| ⭐ **A3 流水只追加** | **3 条 DB 守卫触发器**禁 UPDATE / DELETE / `INSERT OR REPLACE` 复用键（比原 D5 的应用层约定更硬）；错了走红字冲销 |
| ⭐ **触发器只做守卫** | 触发器体内只允许 `SELECT` + `RAISE(ABORT)`，**禁止**写业务表 / 改 `NEW` / 算数量余额；折算、累加、红冲、`balance_after` 全在应用层单一事务；体检脚本扫 `sqlite_master.sql` 自动拦截 |
| ⭐ **流水幂等先查后写** | `stock_ledger` 一律普通 INSERT，禁用一切 OR 冲突策略（`OR IGNORE` 会被第 3 条触发器变成报错）；重复点过账走应用层判定 |
| ⭐ **A4 业务日期优先** | 期间口径一律 `occurred_at`（取订单 `date`），**不用 `created_at`** |
| ⭐ **A5 盘点有时点** | `stock_counts.as_of` 建单即写；提交按「实盘 − 基准 − 期间变动」算差额 |
| ⭐ **A6 已过账不可解锁** | 解锁前查 `stock_postings`，有非冲销 `posted` 批次 → 403；要改先红冲 |
| ⭐ **A7 改账必留操作人** | `AuditLog.log()` 自动注入 `operator_id`；改账 API 校验 `current_operator`；归零强制 `memo` |
| ⭐ **A8 启用唯一入口** | 重新启用只走盘点 / 归零（写 `adjust`），不提供只置 flag 的快捷启用 |
| ⭐ **跳过清单要闭环** | 补过账成功后按 `record_id` 回写 `stock_posting_skips.resolved=1`，否则 `list_unresolved()` 变噪音墙 |
| ⭐ **阶段 0 收尾两项（可选）** | 规格 `*`/空格归一（唯一解才接受，可救约 17 行）；`aux_unit` 保护 + 与 `product_units` 一致性校验（实测 16 个品名不一致） |

## 四、风险登记

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **同名同规格多 SKU**（D-1 的直接后果） | 靠品名认货会认错 | **两道防线**：① 数据库 `uk_product_name_spec` 拦「精确重复 + 规格留空重复」；② 引擎「重复键作废」兜「只差空格的变体并存」→ 走待人工。**每次建档后跑 `_verify_match_precision.py`** |
| R2 | 并发双击过账 | 库存翻倍 | 三道防线（uniq_key / BEGIN IMMEDIATE / UNIQUE 约束） |
| R3 | 折算规则按错品名查 | 「支→码」大面积误判失败 | 引擎已修；**复用引擎，别在蓝图里重写折算** |
| R4 | 部分过账后补数据 | 重复入账 / 漏入账 | 行级幂等；判据第 5 条专测 |
| R5 | 盘点期间发生出入库 | 提交的调整额算错 | ⭐ **A5 取代原四值弹框**：`stock_counts.as_of` 切分期间流水，按「实盘 − 基准 − 期间变动」算差额并逐笔确认；或 `open` 期间禁止对该范围 SKU 过账 |
| R6 | DROP COLUMN 不可逆 | 存量丢失 | 存档 CSV（已完成）；DROP 前再核对 |
| R7 | 库在跑的时候数字漂 | 验收对不上 | 每个阶段的完成判据都要求**注明测量时点** |
| R8 | ⭐ **A2 模型层自带 commit → 事务被拆** | 流水已写、余额没更新，且没人能发现 | 模型方法加 `conn=None`；过账蓝图层持有唯一 `BEGIN IMMEDIATE` 连接；阶段 3 判据 8 专测中途异常全回滚 |
| R9 | ⭐ **A1 REAL 累加残差** | 余额与 `SUM(ledger)` 不严格相等，「冲销回退到 0」偶发失败（实测 `-3.58e-12` vs `0.0`） | 比较一律容差 `1e-6`；流水记 `balance_after`；每阶段收尾跑 `verify_stock_balance.py` |
| R10 | ⭐ **A6 过账后解锁改明细** | 单据数量变了、库存因行级幂等**静默**不更新 | 解锁前查 `stock_postings` → 403「请先红字冲销」 |
| R11 | ⭐ **A7 免登录 + `user_id` 为 NULL** | 改账无操作人，D-4 的「留痕」形同虚设（实测 **20067 / 20171** 行为 NULL） | `AuditLog.log()` 自动注入；改账 API 校验 `current_operator`；移动端用盘点单号限定范围 |
| R12 | ⭐ **A4 / A5 缺业务日期与盘点时点** | 补录旧单归错期间；盘点「先数后入」与「先入后数」结果相反 | 流水加 `occurred_at`；盘点单加 `as_of`；提交列期间流水人工确认 |
| R13 | ⭐ **A8 重新启用口径分歧** | §3.2 / 阶段 7.3 / 接口表三处说法不一，停用期累计被当成可信数 | 唯一入口 = 盘点 / 归零（写 `adjust`）；`enable=true` 降级为纠错 |
| R14 | **`product` 悬空 FK（现实阻塞，非设计缺陷）** | `weight_category_id → product_weight_categories`（表已 DROP）→ FK=ON 下 `product` INSERT/DELETE 报错，**补建档闭环断掉** | 阶段 3 前修（重建表或去 FK）；补建档是消化 116 行待人工的必要动作 |
| R15 | ⭐ **`INSERT OR REPLACE` 绕过禁改触发器** | SQLite 默认 `recursive_triggers=0`，REPLACE 删旧行不触发 DELETE 触发器 → 实测可无声把流水 `10` 改成 `999` | 第 3 条 `BEFORE INSERT ... WHEN EXISTS(uniq_key)` 守卫（无需开 PRAGMA）；`stock_ledger` 禁用一切 OR 冲突策略；A1 `balance_after` + 对账兜底 |
| R16 | ⭐ **触发器承载业务计算** | 库存出现第二套隐式算法，与 `inventory_engine.py` 口径漂移；`balance_after` / A1 对账失真；行级触发器难测 | 硬规则：触发器只允许 `SELECT` + `RAISE(ABORT)`；`stock_schema_check.py` 扫 `sqlite_master.sql` 拦截写关键字；业务计算全归应用层 |

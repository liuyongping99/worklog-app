## 〇、结论先行：推荐落地方式

> 这是看完实际使用痕迹后的推荐。核心一句话：
> **把 `product.stock_quantity` 从「当前库存字段」重新定义为「期初库存（opening）」，
> 库存底下存三类流水（`opening` / `inbound` / `adjust`），
> 并把「期初导入」作为 M1.5 插在建表与过账上线之间。**

### 推荐的三条

**R1. `product.stock_quantity` 直接废弃（DROP COLUMN），库存全部搬到 `product_stock`**

用户已明确拍板。落地要点：
- **先存档再删列**：910 条存量必须先导出 CSV 存档（M1.5），再 DROP —— ⚠️ **不导入库存**（期初数不准，库存靠盘点起算，见 §〇 R2）
- **`aux_quantity` 一并废弃** —— 它是「同一数量的辅助单位表达」（`'2吨4335.777张'`），908 行有值，**同样是数量、同样分仓**，留着就是描述一个已不存在的数
- **`aux_unit` 必须保留** —— 它是**换算关系**（`'1支=46码'`），不是数量。而且它现在是**主力折算规则源**（见 R4）
- **DROP 的安全前提已核实**：SQLite 3.45.3 支持 `ALTER TABLE ... DROP COLUMN`；该字段**无索引、无触发器、无视图**引用 → 可安全删除

**R2. 历史入库单不回填 —— 这不只是省事，是数学上必须的**

正度灰板 250g：存量 `15971.777` 张，而库内历史入库单累计只有 `4900`（3 行）。
**存量已经把历史进货包进去了。** 若再回填 372 张历史单 → `15971 + 4900` = 双重计算。

→ 你选的 D3 得到数据证明。同理，「库存从 0 起」要改成 **「库存从期初起」**，否则第一次过账后库存只有新进货（现实是几万吨），那是错的。

**R3. 「盘点调整」要做 —— 它是旧手工编辑能力的正规化，不是新功能**

用户现在靠产品页手改 `stock_quantity` 调数（343 行小数、`aux_quantity` 自由文本都是痕迹）。
正确做法：编辑能力搬到**库存页**，改数字 → 自动写一条 `adjust` 流水 → 审计链完整、旧字段退役。

**R4. ⭐ 修正：`aux_unit` 才是主力折算规则源，可过账率 62% → 81%**

原方案只用了 `product_units`(83 行) 做折算。实测发现 **`product.aux_unit` 里就写着换算关系**（1477 行全部可解析）：
`'1支=46码'`(126) / `'1支=36.5码'`(104) / `'1支=92码'`(73) / `'1支=48.5码'`(70) / `'1支=55码'`(53) / `'1吨=5818张'`…

| 折算规则来源 | 可过账 | 折算失败 |
|---|---|---|
| 仅 `product_units`（原方案） | 726 (62%) | 218 (18%) |
| **+ `aux_unit` 规则** | **941 (81%)** | **3 (0.3%)** |

→ **M0 不需要「补 YPP 规格规则」了**，规则基本都在 `aux_unit` 里。
→ **唯一瓶颈只剩「product 表缺品名」215 行**。

折算优先级（**规格级优先，品名级兜底**）：
`product_units`(规格级 YPP) → `product.aux_unit`(品名级) → `piece_conversions`(件)
交叉校验：209 个品名两处一致，16 个不一致（如 `杂胶` aux_unit=34.5 vs product_units=36.5/43/44）→ 规格级的 `product_units` 优先。

### 修正：原方案里「令需要确认换算」是错的 ❌

实测逐单位核对（`base_unit` 是否与入库单位一致）：

| 入库单位 | 行数 | `base_unit` 相同（直接可入账） | 不同（需换算） | 无 product |
|---|---|---|---|---|
| 令 | 15 | **15** | 0 | 0 |
| 块 | 36 | 34 | 0 | 2 |
| 卷 | 3 | 3 | 0 | 0 |
| 斤 | 1 | 1 | 0 | 0 |
| 桶 | 64 | 48 | 0 | 16 |
| 张 | 69 | 66 | 0 | 3 |
| 件 | 7 | 0 | 2 | 5 |
| 箱 | 1 | 0 | 0 | 1 |

→ **「令」「块」「卷」「斤」根本不需要换算**，`base_unit` 就是它本身。
**真实的换算缺口是「支→码」213 行** —— ⚠️ **此结论已被 §〇 R4 修正：那些规则本来就在 `aux_unit` 里，不是真缺口**（实测折算失败只剩 3 行）。
→ 再次印证：**瓶颈是 product 建档，不是换算规则。**

### 修正：`stock_quantity` 有一行脏数据 ⚠️

`product_id=1280` 黑磅布三文治 `0.8中性` → `stock_quantity = '31420.@parent_id'`
（**文本脏值**，`@parent_id` 明显是某次批量拼接时混进来的 SQL 片段）

→ 期初导入脚本必须**按类型 + 数值双重校验**，文本值一律拦截并人工确认，不能直接 CAST。

### ⭐ 启用机制（最终版，用户拍板）

**每个商品在每个仓库的库存，默认不启用。执行「盘点」或「归零」后，该商品在该仓的库存才开始计数；
此后入库 / 出库 / 装柜的动作才对库存数量有加减。**

| | 内部流水 | 内部 `quantity` | 对外呈现的库存 |
|---|---|---|---|
| **未启用**（`is_tracking=0`） | ✅ 照记 | ✅ 照常累加 | **0**（置灰，标注「未启用」） |
| **已启用**（`is_tracking=1`） | ✅ 照记 | ✅ 照常累加 | `quantity`（真实余额） |

- **启用唯一入口 = 盘点 / 归零**，绝不自动触发
- **盘点 = 对齐**：内部累计 vs 实际盘点数的差额 → 一条 `adjust` 流水入账；置 `is_tracking=1`
- **归零 = 盘点填 0**（快捷按钮）
- **不会重复计算**：盘点填的「当前实际库存」天然包含未启用期间已入库的货

## 一、已确认的决策

| # | 决策点 | 结论 | 依据 |
|---|---|---|---|
| D1 | 库存粒度 | **只按 `product` 表 SKU 建库存**（键 = `product_id`） | 入库明细里 product 表找不到对应商品的行走「跳过 + 待处理」，不另建文本键兜底 |
| D2 | 单位口径 | **统一折算到 `product.base_unit`** | 换算走现有 `product_units`(YPP) / `piece_conversions`；缺规则的挂起人工处理 |
| D3 | 历史数据 | **先不回填**（历史入库单不回填） | **实测证明必须**：存量已含历史进货（正度灰板存量 15971.777 vs 库内累计入库 4900），回填 = 双重计算。起改用「期初导入」见 §〇 R2 |
| D4 | 过账前置 | **必须先锁定（已核查）才能过账** | 沿用 `inbound_orders.is_locked` 现有语义 |
| D5 | 过账后改错 | **红字冲销**（主流 ERP 做法） | 库存底下存流水不存可改数字；红字单冲回，原记录永不删改 |
| D6 | 幂等粒度 | **明细行级**（同一 `record_id` 只入账一次） | 一张单可分次过账（补完数据继续过），比单据级幂等更实用 |
| D7 | 仓库 | 默认「芙蓉仓」，仓库进 `warehouses` 表可扩展 | `warehouses` 表 + 三张订单表 `warehouse_id` 默认 1 |
| D8 | 旧字段 | **`product.stock_quantity` + `aux_quantity` 直接 DROP** | 库存全搬 `product_stock`；`aux_unit`（换算关系）保留 |
| D9 | 启用机制 | **默认不启用；「盘点」或「归零」后才开始计数** | 未启用时对外一律显示 0，区别于「真 0」 |
| D10 | 盘点范围 | **单仓设计**（`warehouse_id` 固定 1 = 芙蓉仓） | 用户 2026-11-16 拍板。接口仍按 `warehouse_id` 参数设计，将来加田心仓时可扩展 |

> D5/D6 的行业依据：用友 U8 / 金蝶 K3 / SAP 的通用做法是「已记账凭证不可删除、不可原地改，错了走红字冲销（负数单据）」；未跨期时也可「反审核退回 → 改 → 重新记账」。本方案取其**流水账 + 红字冲销**的骨架，并补上丰源场景需要的**部分过账**能力。

### 3.2 `product_stock` 当前库存（仓库 × SKU）

```sql
CREATE TABLE IF NOT EXISTS product_stock (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    warehouse_id  INTEGER NOT NULL,
    product_id    INTEGER NOT NULL,
    quantity      REAL    NOT NULL DEFAULT 0,      -- 折算到 product.base_unit;is_tracking=1 时有效
    is_tracking   INTEGER NOT NULL DEFAULT 0,      -- 1=已纳入库存计算;0=未纳入(对外按 0 处理)
    tracking_started_at TEXT,                     -- 纳入库存计算的起始时刻
    updated_at    TEXT DEFAULT (datetime('now','localtime')),
    UNIQUE(warehouse_id, product_id),
    FOREIGN KEY (warehouse_id) REFERENCES warehouses(id),
    FOREIGN KEY (product_id)   REFERENCES product(product_id)
);
```

#### ⭐ `is_tracking`：区分「真 0」和「不算（数不准）」

用户需求（最终版）：**每个商品在每个仓库的库存信息，默认不启用。
执行「盘点」或「归零」之后，该商品在该仓库的库存才开始计数；
此后入库 / 出库 / 装柜的动作才对库存数量有加减。**

| `is_tracking` | 含义 | 对外呈现的库存 | 参与缺货判断 |
|---|---|---|---|
| `0` | **未启用**（这个商品在这个仓还没开始计数） | **0** | ❌ 不参与（不能因为"0"就报缺货，那不是真缺） |
| `1` | **已启用**（已盘点/归零，计数中） | `quantity`（真实余额） | ✅ 参与 |

**启用规则（唯一入口 = 盘点 / 归零）**

| 操作 | 含义 | 动作 |
|---|---|---|
| **盘点** | 录当前实际库存 N | 写一条 `adjust` 流水把余额对齐到 N → `is_tracking=1` + `tracking_started_at=now` |
| **归零** | 认定当前实际库存为 0 | 同上，N=0（等价于「盘点填 0」，提供快捷按钮） |

- **启用是显式的，绝不自动触发** —— 第一次入库过账**不会**自动启用
- **启用前，进出库流水照记**（内部 `quantity` 照常累加），只是**不对外呈现**（显示 0）
  → 这样流水链始终完整，且盘点时能拿内部累计值跟实际数对账
- **盘点是真正的「对齐」**：内部累计 vs 实际盘点数的差额，用一条 `adjust` 流水入账
  - 相等 → 不写 adjust，只置 `is_tracking=1`
  - 不等 → 写 adjust（差额），流水里能查到「为什么对不上」
- **停用**：库存页可手动 `is_tracking=0`（"这个数我不敢信"）→ 对外显示 0，**流水全部保留**；
  ⭐ **A8（§3.9）：重新启用只能走「盘点 / 归零」**（写 `adjust` 对齐到实际数），
  **不提供「只置 flag、直接显示内部累计」的快捷启用** —— 停用期间的累计同样「不敢信」

**为什么这样设计**
- 「真 0」和「没算」必须能区分 —— 否则满屏 0 分不清是真没货还是没开始算
- 盘点时用户填的是**当前实际库存**，天然包含「启用前已入库但未计入」的货 → **不会重复计算**
- 「归零」单独存在的意义：清仓后重新计数，从 0 起算

**连带规则**
- 红字冲销后 `quantity` 回到 0 → `is_tracking` **保持 1**（这是「真 0」）
- 出库 / 装柜扣减**不会**自动启用（没盘点过就没有可信基线）
- 出库 / 装柜在**未启用**时：流水照记（对称），对外仍显示 0

**期初快照的处置** ⚠️
既然启用靠盘点、期初数不准：
- **不批量导入为库存基数**（`product_stock` 从空表起步）

  （列：`product_id, product_code, product_name, specification, base_unit, aux_unit, stock_quantity, aux_quantity, warehouse, stock_state, note`）
- ⇒ 原方案的 **M1.5「期初导入」降级为「导出存档」**，不再是必做阶段

### 3.3 `stock_ledger` 库存流水（一切的唯一来源）

三类流水共用一张表，靠 `biz_type` + `uniq_key` 区分幂等语义：

| `biz_type` | 含义 | `uniq_key` | 触发 |
|---|---|---|---|
| `adjust` | **盘点 / 归零 / 人工调整**（把余额对齐到实际值） | `adjust:{seq}` | 库存页「盘点」「归零」「改数」 |
| `inbound` | **入库**过账（+） | `inbound:{record_id}` | 入库单过账按钮 |
| `outbound` | **出货**扣减（−） | `outbound:{record_id}` | 出货单过账按钮 |
| `loading` | **装柜**扣减（−） | `loading:{record_id}` | 装柜单过账按钮 |
| 任意 + `is_reversal=1` | **红字冲销** | `{biz_type}:{record_id}:rev` | 冲销按钮 |

```sql
CREATE TABLE IF NOT EXISTS stock_ledger (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    warehouse_id  INTEGER NOT NULL,
    biz_type      TEXT    NOT NULL,               -- 'opening' | 'inbound' | 'adjust' | 'outbound'
    uniq_key      TEXT    NOT NULL,               -- 幂等键,见上表
    order_pk      INTEGER NOT NULL DEFAULT 0,     -- 入库单 id;opening/adjust 为 0
    record_id     INTEGER NOT NULL DEFAULT 0,     -- 入库明细行 id;opening/adjust 为 0
    product_id    INTEGER NOT NULL,
    quantity      REAL    NOT NULL,               -- 基本单位数量；红字为负
    unit          TEXT    NOT NULL,               -- 折算后的基本单位
    raw_quantity  REAL    NOT NULL DEFAULT 0,     -- 原始数量
    raw_unit      TEXT    NOT NULL DEFAULT '',    -- 原始单位
    factor        REAL    NOT NULL DEFAULT 1,     -- 折算系数
    is_reversal   INTEGER NOT NULL DEFAULT 0,     -- 1=红字冲销
    posting_id    INTEGER,                        -- 关联过账批次
    operator_id   INTEGER,
    memo          TEXT    NOT NULL DEFAULT '',    -- 调整原因 / 期初来源说明
    occurred_at   TEXT    NOT NULL DEFAULT '',    -- ⭐A4 业务日期,取订单 date;期间汇总/盘点截止一律用它
    balance_after REAL,                          -- ⭐A1 本笔记账后该(仓,SKU)的余额快照
    unit_cost     REAL,                          -- ⭐B档 已落列(可空):每个**基本单位**的成本;V1 不写
    amount        REAL,                          -- ⭐B档 已落列(可空):本笔金额 = quantity × unit_cost;V1 不写
    created_at    TEXT DEFAULT (datetime('now','localtime')),  -- 记账时刻(系统时间,不用于期间汇总)
    UNIQUE(uniq_key),
    FOREIGN KEY (warehouse_id) REFERENCES warehouses(id),       -- ⭐阶段 1.6
    FOREIGN KEY (posting_id)   REFERENCES stock_postings(id)    -- ⭐阶段 1.6(可空:adjust/opening 无批次)
);

-- ⭐A3 只追加:数据库层禁止改 / 删流水(光靠应用层约定挡不住手工 SQL)
-- 三条全部是「守卫型」:只读 SELECT + RAISE(ABORT),不写表 / 不改 NEW / 不做任何数量计算
CREATE TRIGGER IF NOT EXISTS trg_stock_ledger_no_update
BEFORE UPDATE ON stock_ledger
BEGIN SELECT RAISE(ABORT, 'stock_ledger 只可追加;改错请走红字冲销'); END;
CREATE TRIGGER IF NOT EXISTS trg_stock_ledger_no_delete
BEFORE DELETE ON stock_ledger
BEGIN SELECT RAISE(ABORT, 'stock_ledger 只可追加;禁止删除'); END;
-- 第 3 条:堵住 INSERT OR REPLACE / UPSERT 绕过(SQLite 默认 recursive_triggers=0,
-- REPLACE 删旧行时不触发 DELETE 触发器;实测可无声把 quantity 10 改成 999)。
-- BEFORE INSERT 触发时冲突旧行尚未删除 → EXISTS 仍查得到,故无需开任何 PRAGMA。
CREATE TRIGGER IF NOT EXISTS trg_stock_ledger_no_reuse
BEFORE INSERT ON stock_ledger
WHEN EXISTS (SELECT 1 FROM stock_ledger WHERE uniq_key = NEW.uniq_key)
BEGIN SELECT RAISE(ABORT, 'uniq_key 不可复用;禁止 REPLACE / UPSERT 改账'); END;
```

**A 档新增 2 列的写入契约**（`stock_ledger` 是全库唯一真值源，列不能只加不写）：

| 列 | 谁写 | 规则 |
|---|---|---|
| `occurred_at` | 过账 / 冲销 / 盘点提交 | 取**订单头 `date`**（`inbound_orders` / `shipping_orders` / `loading_orders` 都有此列）；`adjust` 无订单 → 取盘点单 `as_of` 或当天；**格式 `YYYY-MM-DD`，留空即视为数据缺陷** |
| `balance_after` | 同一 `BEGIN IMMEDIATE` 事务内 | 写流水前先算出本笔之后的 `product_stock.quantity`，随流水一起落库；红冲同样记回冲后的余额 |

**B 档成本 2 列的写入契约（V2 才用，V1 留空）** ⭐ 2026-11-16 用户拍板「先加列，成本法 V2 再定」：

| 列 | 谁写 | 规则 |
|---|---|---|
| `unit_cost` | V2 做金额账时 | **每个 `product.base_unit` 的成本**（不是原始单位的价）—— 主流进销存的通行口径：单价跟着**库存基本单位**走，换算系数一变，单价要同步折算 |
| `amount` | V2 做金额账时 | `= quantity × unit_cost`（红字为负）；`quantity` 是折算后的基本单位数量 |

> ⚠️ **为什么必须现在就落列（而不是等 V2 再加）**：
> 本表有 A3 禁改触发器 → **流水一旦落库就物理上改不了**。
> 若 V2 才加这两列，已有的历史流水**无法回填成本单价** → 期初成本缺失 →
> 「期初 + 本期入 − 本期出 = 期末」对不上，移动加权 / FIFO 都算不出准确金额账。
> 现在表还全空，加两个可空列零成本；错过这个窗口就只能**另起一套账**。
>
> ⚠️ **成本核算方法（移动加权平均 / FIFO）V2 再定**（用户 2026-11-16 拍板，V1 不预设）。
> 但要知道这个选择的连带影响：**FIFO 必须有批次号**（要连带做批次/效期表），
> **移动加权不需要批次**，与现有无批次表结构兼容 → V1 存的 `raw_quantity` / `raw_unit` / `factor` 已经够算。

> ⚠️ **RED 精度口径**：`quantity` / `balance_after` / `product_stock.quantity` 都是 REAL，
> 而 `支→码` 走 36.5/46/92、`件→张` 走 5818/7 这类非整系数 → 逐笔累加与 `SUM(ledger)` **不严格相等**
> （实测 300 笔入 + 300 笔红冲：逐笔 UPDATE 余额 `-3.58e-12`，`SUM(ledger)` `0.0`）。
> ⇒ **所有余额比较与判据一律用容差 `1e-6`，禁止 `== 0`**；对账脚本见 §3.9 A1。

**`stock_ledger` 幂等写入契约**（第 3 条触发器的直接后果，阶段 3 必须遵守）：

| 允许 | 禁止 |
|---|---|
| 普通 `INSERT INTO stock_ledger (...)` | `INSERT OR REPLACE` / `INSERT OR IGNORE` / `ON CONFLICT DO UPDATE` / `ON CONFLICT DO NOTHING` |
| 写前按 `uniq_key` **查 `stock_postings` / ledger 先判定**（幂等跳过） | 依赖 OR 冲突策略「静默跳过」 |
| `UNIQUE(uniq_key)` 冲突 → `IntegrityError` 转「已过账」提示 | 用触发器或冲突策略隐式改数 |

> 第 3 条触发器会把 `OR IGNORE` / `DO NOTHING` 从「静默跳过」变成「报错」→ **行级幂等必须走先查后写**，
> 而不是靠 SQL 冲突策略。此约束**只针对 `stock_ledger`**，其它表（如 `warehouses` 的 `INSERT OR IGNORE`）不受影响。
> 三条触发器一律只做守卫，业务计算归属见 §3.9「A3 · 触发器只做守卫」。
> 将来若要根治（改成整数最小单位存储，参照 `product_units.yards_per_piece` ×100 的既有做法），属独立重构，不在 V1。

### 3.7 盘点单表（盘点作业的单据，对齐 `point_count` 的会话模式）

盘点是**一项作业**：拿清单去数、分几批录、最后统一提交。所以要有单据，不是弹框。

```sql
-- 盘点单
CREATE TABLE IF NOT EXISTS stock_counts (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    warehouse_id  INTEGER NOT NULL DEFAULT 1,     -- 单仓设计：固定 1（芙蓉仓）
    title         TEXT    NOT NULL,               -- '11月全仓盘点'
    remark        TEXT    NOT NULL DEFAULT '',
    status        TEXT    NOT NULL DEFAULT 'open',-- 'open' | 'closed'
    total_items   INTEGER NOT NULL DEFAULT 0,    -- 应盘商品数
    counted_items INTEGER NOT NULL DEFAULT 0,    -- 已录数
    diff_items    INTEGER NOT NULL DEFAULT 0,    -- 有差异数
    created_by    INTEGER,
    created_at    TEXT    NOT NULL,
    as_of         TEXT    NOT NULL DEFAULT '',  -- ⭐A5 盘点基准时点(建单时刻);提交时按它切分期间流水
    closed_at     TEXT,
    FOREIGN KEY (warehouse_id) REFERENCES warehouses(id)     -- ⭐阶段 1.6
);

-- 盘点明细（每个商品一行，存实盘数）
CREATE TABLE IF NOT EXISTS stock_count_items (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    count_id        INTEGER NOT NULL,
    product_id      INTEGER NOT NULL,
    book_quantity   REAL    NOT NULL DEFAULT 0,  -- 账面数（建单时快照）
    actual_quantity REAL,                        -- 实盘数；NULL = 待录
    counted_at      TEXT,
    UNIQUE(count_id, product_id),
    FOREIGN KEY (count_id) REFERENCES stock_counts(id)
);
```

**`book_quantity` 是建单时的快照**，作用是显示「账面 vs 实盘」的差异。
⚠️ ⭐ **A5（§3.9）：提交时调整的目标既不是 `book_quantity`，也不能只按「当前实际余额」算** ——
「现场数完货之后又入库」与「先入库再数货」，**同样两个数、顺序相反、结果相反**，而旧口径无法判断顺序。
差额 = `actual_quantity` − **截至 `as_of` 的基准余额** − **`as_of` 之后的期间变动**
（按 `occurred_at` 切分流水，逐笔列出供人工确认）
→ 提交确认弹框展示「账面 → 实盘 → 期间变动 → 基准余额 → 最终调整额」，流程见 §4.3。

**「归零」不需要单独的单据表** —— 它就是一次操作，直接写 `adjust` 流水 + 置 `is_tracking=1`，审计链在流水表里。

> ⭐ **2026-11-17 阶段 3 落地补正 —— A6 的判据是「流水」不是「批次状态」**：
> 上表 A6 写的是「查 `stock_postings`，存在非冲销的 `posted` 批次 → 403」。
> 实测发现这个判据**不够准**：
> 「重复点过账」会留下一条 `posted_count=0` 的**空批次**，status 同样是 `'posted'`
> → 拿批次状态当判据，会在**冲销之后仍然 403**，订单再也解不了锁。
>
> **正解**：判据是「**还有没被冲销的入账流水**」
> （有一行正向流水、且没有对应的 `:rev` 冲销流水 → 才算「还欠一笔」）。
> 流水才是「库存真的记了这笔账」的证据。
> 落地：`blueprints/stock_posting.py:has_live_posting()`。
> 另外，纯幂等空转**不建批次**了（批次语义 =「一次真正入账的动作」）。
>
> ⚠️ **教训**：状态位是「派生值」，判据尽量用**流水**这种「真值源」——
> 这跟 A1「`product_stock` 只是流水的缓存」是同一条原则。

#### A1 · 对账是硬不变量，不是可选工具

`StockLedger.sum_by_product()` 已有，但阶段 1 的 `stock_schema_check.py` **只查表结构不查数据**，
验收 16 条里也没有「余额重算」断言。`tools/verify_stock_balance.py` 要校验三件事：
① 逐 (仓, SKU) `abs(product_stock.quantity − SUM(stock_ledger.quantity)) < 1e-6`；
② `balance_after` 逐笔链连续（上一笔 `balance_after + 本笔 quantity == 本笔 balance_after`）；
③ `occurred_at` 非空。
**演练默认，差异只打印不自动修**；要修必须显式 `--apply` 且先 WAL 备份（沿用既有安全链）。
阶段 3 的测试加一条不变量测试：随机生成 N 笔 入 / 冲销 / 调整，末了重算余额并断言一致。

> ⭐ **`--apply` 的语义（2026-11-16 定）**：**只做一件事 —— 以流水为准，重算并回写
> `product_stock.quantity`**。缓存是派生值、流水是真值源（A1），所以这是「重建缓存」不是「改账」。
> **`--apply` 绝不改历史流水** —— A3 触发器也不允许；`balance_after` 链断 / `occurred_at` 为空
> **只报告、不可修**（改错只能写一条红字流水，那是记账不是修账）。
> 这条同时解掉了「A3 禁改触发器」与「1.5.6 的 `--apply` 要能修」之间的矛盾。

#### A2 · 模型层不能自带 commit

现状 `models/inventory.py` 每个方法 `get_db()` → `commit()` → `close()`，
`add_quantity()` 里 `ensure()` 先提交一次、UPDATE 再提交一次 → 与 §4.2「单事务写 4 张表」**直接冲突**。
改造形态（二选一，阶段 3 开工前定）：
① 模型方法统一加 `conn=None`，传入则复用连接且不 commit；过账蓝图持有唯一连接并 `BEGIN IMMEDIATE`；
② 写独立 `posting_service.py`，直接 SQL 操作 4 张表，模型层只保留查询方法。
`product_stock` 的原子 `UPDATE quantity = quantity + ?`（`models/inventory.py:149`）**保持不动，它是对的**。

> ✅ **2026-11-17 阶段 3 落地：选 ①**。
> 理由：模型层已有 `create_if_absent()` 等**已验证**的入口，② 会绕开它们；
> 且「库存数字只能有一个源头」要求余额累加仍只有 `ProductStock.add_quantity()` 一处。
> → **事务编排**放在 `blueprints/stock_posting.py`（服务层，494 行），
> **HTTP 端点**放在 `blueprints/stock.py`；模型层只提供「可传入外部连接」的能力。
>
> ⚠️ 落地时踩到的两个 SQLite 细节（写同类代码前先知道）：
> ① Python `sqlite3` 默认 `isolation_level=''` 会**隐式管事务**，与显式 `BEGIN IMMEDIATE` 打架
>    （典型报错 `cannot start a transaction within a transaction`）
>    → 事务连接必须先 `conn.isolation_level = None`，事务全部显式 BEGIN / COMMIT / ROLLBACK。
> ② `sqlite_sequence` **没有** UNIQUE 约束（`name` 不是主键）→ 写它只能用
>    `UPDATE` + 条件 `INSERT`，**不能**用 `ON CONFLICT(name) DO UPDATE`。

#### A3 · 触发器只做守卫，禁止承载业务计算

**硬规则**：`stock_ledger` 上的触发器只允许出现 `SELECT`（只读存在性判定）+ `RAISE(ABORT)`；
**禁止**在触发器体内 `INSERT` / `UPDATE` / `DELETE` 任何业务表、禁止给 `NEW` 赋值、禁止计算数量 / 余额 / 折算。
`tools/stock_schema_check.py` 扫描 `sqlite_master.sql` 自动检查：触发器定义里出现上述写关键字即判失败（阶段 1.5.5 / 验收 25）。

| 环节 | 归属（唯一源头） |
|---|---|
| 单位折算 / YPP / SKU 匹配 | `blueprints/inventory_engine.py` |
| 余额累加 | `models/inventory.py:add_quantity()` 的 `UPDATE quantity = quantity + ?` |
| 红字冲销 | 应用层 INSERT 一条负数量流水，**不是触发器自动生成** |
| `occurred_at` / `balance_after` | 同一 `BEGIN IMMEDIATE` 事务内由过账 / 冲销 / 盘点服务算好后随流水一起 INSERT（§3.3 写入契约） |

理由：① 库存数字只能有一个源头，触发器里藏第二套算法必然与引擎口径漂移，且是隐式的；
② A2 要求单事务写 4 张表，触发器若偷偷改 `product_stock` 就成了不可见的第二写入点，`balance_after` 快照与 A1 对账都失真；
③ SQLite 触发器只有行级、无调用栈、pytest 难覆盖，`recursive_triggers` 默认 OFF 会让链式行为随连接变化。
**触发器只防「手滑 SQL」，不防「有意改库」**（`DROP TRIGGER` / `PRAGMA writable_schema` 可绕过）→
终极兜底仍是 A1 的 `balance_after` + `verify_stock_balance.py`。

**为什么必须是 3 条**：实测 SQLite 3.45.3，前两条能挡 `UPDATE` / `DELETE`、放行正常 `INSERT`，
但 `INSERT OR REPLACE` 在默认 `recursive_triggers=0` 下**不触发 DELETE 触发器** → 可无声把流水数量从 `10` 改成 `999`。
第 3 条 `BEFORE INSERT ... WHEN EXISTS(...)` 在冲突旧行被删之前触发，故能同时拦住
`INSERT OR REPLACE` / `ON CONFLICT DO UPDATE` / `DO NOTHING` / `OR IGNORE`，**无需开任何 PRAGMA**，
代价是幂等写法必须改成「先查后写」（见 §3.3 写入契约）。
`RAISE(ABORT)` 只撤销当前语句、不回滚同事务先前写入；`RAISE(ROLLBACK)` 会整笔回滚 →
过账是单事务写 4 张表，选 `ABORT`（误伤小）+ A1 对账兜底。

#### A5 · 盘点点位的顺序陷阱

`book_quantity` 是建单快照，提交时按「当前余额」算差额。若现场数完货之后又入库 10 码，
`delta = 实盘 − 当前余额(已含 10)` 会把这 10 码当盘亏吃掉；反过来先入库后数货才是对的。
**同样两个数、顺序相反、结果相反，而现有字段无法判断顺序。**
`as_of` + `occurred_at` 落地后，提交流程改为：
`基准余额 = 截至 as_of 的流水和` → `期间变动 = occurred_at > as_of 的流水和` →
`应调差额 = 实盘 − 基准余额 − 期间变动`，并把期间变动逐笔列出让人确认。
单仓单人也可选更简方案：盘点单 `open` 期间**禁止对该范围 SKU 过账**（写进阶段 5 判据）。

> ⚠️⚠️ **口径陷阱（阶段 5 提交时必须显式处理）**：
> `occurred_at` 是**日期**（取订单 `date`，`YYYY-MM-DD`），`as_of` 是**时刻**（建单时刻，`YYYY-MM-DD HH:MM:SS`）
> → **两者不能直接比大小**。字符串比较下 `'2026-11-16' > '2026-11-16 17:00:00'` 为假，
> 同一天的流水会被判成「基准内」而漏掉「先数货后入库」那部分。
> **建议口径**：`occurred_at > date(as_of)` 的算「期间变动」；
> **同日**流水用 `created_at > as_of` 判定（先入库后数货 = 基准内；先数货后入库 = 期间变动）。
> 这条已写进 `models/inventory.py` 的 `StockCount.create()` docstring。

### 3.10 ⭐ 外键约束（B 方案，2026-11-16 阶段 1.6 落地）

**结论**：5 张库存表**全部**补 FK（`product_stock` / `stock_ledger` / `stock_postings` / `stock_posting_skips` / `stock_counts` / `stock_count_items` 共 8 条）。

**为什么补**（这就是「为什么要加外键」的通俗版）：

- 外键 = 「这一列的值必须指向另一张表里真实存在的那一行」。
  没有它，「流水挂在仓库 3 上，但仓库 3 根本不存在」「跳过明细指向一个已被删掉的过账批次」这类脏数据能悄悄落库，
  直到某天查账才发现，而且**很难定位是哪一步写坏的**。
- **边际代价≈0**：`product_stock.warehouse_id → warehouses(id)` 早就建了 —— 只要该仓有过库存行就已经挡得住删仓；
  且 `warehouses.status` 这个字段的存在说明设计本来就是「**停用代替删除**」，不是「删了再说」。
- **风格统一**：全库另外 24 张表都建了 FK，库存这 5 张是唯一的例外。

**行业主流做法**（2026-11-16 用户问「按行业标准推荐哪个」时的答复）：

| 系统 | 主数据 → 单据 | 明细 → 父单 |
|---|---|---|
| 用友 U8 | 建 FK | 建 FK |
| 金蝶 K3 | 建 FK | 建 FK |
| SAP | 不建 DB FK | 不建 DB FK |

> ⚠️ SAP 不建是**它自己的特殊约束**（表合并 + ABAP 层强制），不是通用标准 ——
> 别拿 SAP 当「不用 FK 也行」的通用理由。本项目是单体 Flask + SQLite，DB 层 FK 就是最省事也最有效的一层。

**⚠️ FK 只当兜底，不当唯一防线**：阶段 3 的过账 API **仍要做应用层校验**
（`Warehouse.get_by_id()` 查不到 → 返回 400 + 中文提示），否则 `IntegrityError` 会变成用户看不懂的 500。

**落地代价**：SQLite 的 `ALTER TABLE` **加不了约束**，只能 `DROP + CREATE` 重建表。
4 张表当时**全 0 行** → 重建零数据损失。重建要过 4 道坎（见 `models/_init.py` 的 `_rebuild_table_for_fk` 注释）：
① `PRAGMA foreign_keys` 事务内 no-op · ② 删被引用的父表要 `legacy_alter_table=ON` · ③ DROP 会连带删索引和触发器 ·
④ 数据搬运必须按列名（不能用 `SELECT *`，新旧列顺序不同）。

## 四、过账流程

### 4.1 三个业务动作对库存的影响

| 动作 | 符号 | 流水 `biz_type` | 订单表 | 备注 |
|---|---|---|---|---|
| **入库** | **+** | `inbound` | `inbound_orders` | 锁定后点「过账」 |
| **出货** | **−** | `outbound` | `shipping_orders` | 锁定后点「过账」→ 货离仓 |
| **装柜** | **−** | `loading` | `loading_orders` | 锁定后点「过账」→ 货装柜离仓 |
| 盘点/归零 | 调整 | `adjust` | — | 库存页批量操作 |

> ⚠️ **出货/装柜扣减的「时点」待定**（见 §十）：建议与入库对称 —— **订单锁定（核查完成）时扣减**，
> 因为锁定 = 你确认这张单没问题了 = 货确实要发。若你更希望「实际发货时才扣」，则触发点改成另一个动作。
> 扣减后若 `quantity` 变负 → 允许（说明超卖/账实不符），但库存页要标红提示。

### 4.2 入库过账流程（出货/装柜同构，只是符号相反）

```
用户点「📥 过账」（出货/装柜为「📤 扣减」）
   │
   ├─ 闸门1：订单必须 is_locked=1        → 否则 409「请先核查并锁定该订单」
   ├─ 闸门2：订单必须 warehouse_id 有效
   │
   ├─ 取该单所有明细行（按 sort_order）
   │     ├─ 已在 ledger 有正向流水 → 跳过（幂等），计入「已过账」
   │     ├─ 找不到 product（SKU） → 跳过，reason='no_product'
   │     ├─ product.base_unit 非法/空 → 跳过，reason='bad_base_unit'
   │     ├─ quantity 非数字/≤0 → 跳过，reason='bad_qty'
   │     ├─ 单位 != base_unit 且查不到换算规则 → 跳过，reason='no_conversion'
   │     └─ 以上都过 → 折算 quantity×factor（入库取正 / 出货装柜取负），写 ledger，更新 product_stock
   │
   ├─ ⭐ is_tracking 判定（**不改变启用状态**，只标记）：
   │     ├─ 该 (仓,商品) is_tracking = 0
   │     │     → 流水照记、quantity 照常累加（内部对账用）
   │     │     → 但对外呈现仍是 0 → 收进 not_tracking 清单，提示用户去盘点
   │     └─ is_tracking = 1 → 正常加减，对外呈现随之变化
   │
   ├─ ⭐ 单事务（BEGIN IMMEDIATE + **单一连接**）写入 —— 见 §3.9 A2：
   │     ├─ 模型层**不得自行 commit**;四张表共用同一 conn
   │     ├─ stock_postings(1) + stock_ledger(N) + product_stock upsert + stock_posting_skips(M)
   │     ├─ 每条 ledger 写 occurred_at = 订单.date（§3.9 A4,不用系统时间）
   │     ├─ 每条 ledger 写 balance_after = 本笔后的 product_stock.quantity（§3.9 A1）
   │     ├─ ⭐ ledger 一律**普通 INSERT**,禁用 OR REPLACE / OR IGNORE / ON CONFLICT;幂等走先查后写（§3.3 写入契约）
   │     └─ 中途异常 → 全回滚;UNIQUE(uniq_key) 冲突 → 转「已过账」提示,不报错
   │
   └─ 返回 {posted_count, posted_qty, not_tracking:[...未启用的商品], skipped:[...明细与原因]}
```

> ⭐ **关键约定：过账不改变启用状态。**
> 启用只由**盘点 / 归零**触发（§3.2）。
> 好处：
> ① 启用前后的进出流水都完整保留，盘点时能拿内部累计跟实际数对账
> ② 盘点填的「当前实际库存」天然包含启用前已入库的货 → **不会重复计算**
> ③ 不会出现"过账时自动启用 → 存量突然从 0 跳到旧数"的突兀

> ⚠️ **未启用时入库的货去哪了？**
> 它**进了流水、也进了内部 quantity**，但对外显示 0。
> → 用户盘点时填的实际库存就是对的（已含这批货）→ 盘点后启用，一致 ✅
> → 所以**不需要**「补过账」这一动作，也不会有重复计入的风险。

> ⭐ **2026-11-17 阶段 3 落地补正 —— `not_tracking` 不进 `stock_posting_skips`**：
> `stock_posting_skips` 是「**没入账**的待处理清单」；
> 而 `not_tracking` 的行**已经入账了**（流水照记、内部累计照加，只是对外显示 0）。
> 放进 skips 会让「未入账行数」虚高，也会让「补过账」逻辑误把它当成待补的行
> → 结论：`not_tracking` 单列在过账结果的 `not_tracking[]` 清单里；
> `stock_posting_skips` 只装**真正没入账**的行（`no_product` / `no_conversion` /
> `bad_base_unit` / `bad_qty`）。DDL 里保留 `not_tracking` 这个 reason_code 作为预留。

> ⭐ **2026-11-17 阶段 3 落地补正 —— 「冲销过的行不能再正向过账」**：
> 上文「已冲销的行不再允许再次正向过账(UNIQUE(uniq_key) 约束挡住)」在 V1 的实际表现是：
> 正向 `uniq_key`（如 `inbound:123`）**仍被原流水占着** → 再点过账时「先查后写」会跳过它
> → 库存不会被加回去，接口返回「本单已冲销,不能重复过账」。
> ⇒ **要改单据请改源头再重新建单**，不是解锁改明细（这也是 A6 解锁守卫存在的意义）。

### 4.3 盘点 / 归零流程

```
库存页勾选商品 → 点「盘点」或「归零」→ 填实际数 → 提交
   │
   ├─ 批量：POST /api/v1/stock/inventory
   │     body: {warehouse_id, items:[{product_id, actual_quantity, memo?}], mode:'inventory'|'zero'}
   │
   ├─ ⭐ 闸门0：读盘点单 as_of（§3.9 A5,解决「先数货还是先入库」的顺序陷阱）
   │     ├─ 基准余额 = SUM(ledger WHERE occurred_at <= as_of)
   │     ├─ 期间变动 = SUM(ledger WHERE occurred_at >  as_of) → 逐笔列出供人工确认
   │     └─ 单仓单人可选简案：open 期间禁止对该范围 SKU 过账(写进阶段 5 判据)
   │
   ├─ 对每个 item：
   │     ├─ 差额 delta = actual_quantity − 基准余额 − 期间变动
   │     ├─ delta != 0 → 写一条 adjust 流水
   │     │     (occurred_at = as_of 所在日;balance_after = 调整后余额;
   │     │      memo 记「实际 X / 基准 Y / 期间 Z / 调整 D」)
   │     ├─ delta == 0 → 不写流水，只置 flag
   │     └─ is_tracking = 1, tracking_started_at = now
   │           ⭐A8：这也是「停用后重新启用」的**唯一**入口,不提供只置 flag 的快捷启用
   │
   └─ 返回 {updated: N, adjusted: M, unchanged: K}
```

> **「归零」= 盘点填 0**（`mode='zero'` → `actual_quantity=0`）。
> 库存页给「归零」一个独立快捷按钮，不用每次手填 0。

**单位折算优先级**（全部复用 `blueprints/_helpers.py` 现有函数，不重复造轮子）：

| 源 → 目标 | 规则来源 | 备注 |
|---|---|---|
| `y` → `码` | **别名表，1:1** | 653 行靠这条 |
| 同单位 | 1:1 | `令`/`块`/`卷`/`斤`/`桶`/`张` 全走这条 |
| `支` → `码` | ① `product_units.yards_per_piece`（`get_ypp`，规格级优先）<br>② `product.aux_unit` 解析（品名级兜底，如 `'1支=46码'`） | **主力路径**；aux_unit 覆盖 1477 行 |
| `件` → `张`/`令`/… | `piece_conversions.units_per_piece`（`get_piece_conversion`） | 仅 3 个品名有规则 |
| 其他 | — | 挂起人工处理 |

> ⭐ **实测（纳入 `aux_unit` 后）**：可过账 941/1160 (81%)，折算失败只剩 3 行。
> 唯一瓶颈是「product 表缺品名」215 行。见 §〇 R4。

> **YPP 规则存在但值为 0 的坑**：`product_units` 里有 `0.4无毒平纹`(0.0)、`A级黑`(0.0) 这类 `yards_per_piece=0` 且 `is_usingyardforcounting=0` 的行。折算时 **0 视为「无规则」**，不能当 0 系数入账（否则库存被清零）。
> **aux_unit 解析规则**：`'1支=46码'` → 系数 46；`'1吨=5818张'` → 系数 5818；`'1码'` → 1.0；无法解析则视为无规则（走下一优先级）。

**红字冲销（撤销过账）**：

```
POST /api/v1/{inbound|shipping|loading}-orders/<id>/reverse
   ├─ 找到该单所有 is_reversal=0 的 ledger 行（biz_type 随订单类型）
   ├─ 每条写一条反向 ledger（quantity 取负，is_reversal=1，uniq_key 加 ':rev'）
   ├─ product_stock 相应反向调整（quantity 回到过账前）
   ├─ posting.status='reversed'
   └─ 已冲销的行不再允许再次正向过账（UNIQUE(uniq_key) 约束挡住）
```

**补过账**（补完 product 表 / 换算规则后，把之前跳过的行补进来）：
再点一次「过账」→ 已入账的行走幂等跳过（不重复加），上次跳过的行走正常折算入账 → 因此 `stock_posting_skips` 需按 `record_id` 记 `resolved` 状态。

> ⚠️ **注意区分两类跳过**（避免重复计算）：
> | skip reason | 修好后能否补过账 |
> |---|---|
> | `no_product` / `no_conversion` / `bad_base_unit` / `bad_qty` | ✅ **能**（数据问题，修好即可补） |
> | `not_tracking`（未启用库存计算） | ❌ **不能** —— 盘点的实际库存已包含这批货，补过账会重复计入 |

#### 6.2.1 ⭐ 阶段 2 落地的 3 处关键设计（都是「照计划做会踩」的坑）

**① 主查询以 `product` 为驱动表，不是 `product_stock`**

`product_stock` 只在「盘点 / 归零」之后才会有行 —— 现在是 **0 行**。
若从 `product_stock` 出发 `INNER JOIN product`，库存页上线当天就是**一片空白**。
而库存页**必须**能看到「还没启用库存计算」的商品（显示 0 + 灰色「未启用」标签）——
否则用户根本不知道有哪些货要盘。

→ 改成 `FROM product p LEFT JOIN product_stock ps ON ps.product_id = p.product_id AND ps.warehouse_id = ?`，
1600 个商品全部出现，`ps` 字段用 `COALESCE(..., 0)` 兜底。

**② 「内部累计」必须按仓一次聚合，不能逐行查**

`StockLedger.sum_by_product()` 是单 SKU 一次查询 → 1600 行就是 1600 次查询（N+1）。
→ 新增 `StockLedger.sum_by_warehouse(warehouse_id)`：`GROUP BY product_id` 一次算完，返回 `{pid: qty}`。

**③ 「导出 CSV 与页面逐行一致」是结构保证，不是人工核对**

页面和导出**共用同一个 `_parse_stock_query()` + `_fetch_stock_rows()`**，导出只是不加分页。
筛选口径一处定义，不会分叉。
⚠️ 唯一的差别是 **CSV 注入防护前缀**：品名以 `=+-@` 开头时，CSV 里会多一个 `'`（防 Excel 当公式执行）——
那是**传输层保护**，不是数据变化。

**④ 分类筛选：选父分类要含所有后代**

`ProductCategory.descendant_ids(category_id)` → 否则用户点「白坯布」看不到它的三级子类，会以为货丢了
（主流进销存的通用做法）。

#### 6.4.4 盘点 vs 归零 —— 两者的关系

| | 盘点 | 归零 |
|---|---|---|
| 语义 | 「我现在实际有 N」 | 「我现在实际是 0」 |
| 界面 | `/stock/count`（单据式，可分批） | `/stock/zero`（即时操作） |
| 后端 | `stock_counts` 单据 → `submit` | `POST /api/v1/stock/zero` 直写 |
| 结果 | `adjust` 差额 + `is_tracking=1` | `adjust`（全额归零）+ `is_tracking=1` |

**归零 = 盘点填 0**，两者最终都写 `adjust` 流水 → **审计链统一**。
盘点详情页里的「⭕ 全表归零」就是归零的批量版本，走同一条流水。

### 7.1 `product.stock_quantity` / `aux_quantity` 废弃 ⚠️ 用户已拍板

**决策**：`product.stock_quantity` **直接废弃（DROP COLUMN）**。库存全部搬到 `product_stock`，
页面按**选中的仓库**显示该仓库存。

#### 字段去留对照

| 字段 | 处置 | 理由 |
|---|---|---|
| `product.stock_quantity` | **DROP** | 是数量，且分仓。存量已存档 CSV（1536 行，含 938 行有存量），**不导入**（库存靠盘点起算） |
| `product.aux_quantity` | **DROP** | 是「同一数量的辅助单位表达」（`'2吨4335.777张'`），908 行有值 —— **同样是数量、同样分仓**，留着就是描述一个已不存在的数 |
| `product.aux_unit` | **保留** | 是**换算关系**（`'1支=46码'`），不是数量。**而且它是主力折算规则源**（§〇 R4）→ 要保护，别让人乱改 |
| `product.base_unit` | **保留** | 库存的计量单位，过账折算的目标 |

#### DROP 的安全前提（已核实）

- ✅ SQLite **3.45.3** → 支持 `ALTER TABLE product DROP COLUMN`
- ✅ 该字段**无索引、无触发器、无视图**引用 → 可安全删除
- ⚠️ 有 1 行脏数据 `product_id=1280` 的 `stock_quantity='31420.@parent_id'`（文本）→ 期初导入时拦截

### 7.2 单位语义 —— 已实测澄清，原方案的担心不成立 ✅

原方案写「令/块/箱/卷需要业务确认换算关系」，**实测证明这是错的**：

| 入库单位 | 行数 | `base_unit` 相同（直接 1:1 入账） | 需换算 | 无 product |
|---|---|---|---|---|
| 令 | 15 | **15** | 0 | 0 |
| 块 | 36 | 34 | 0 | 2 |
| 卷 | 3 | 3 | 0 | 0 |
| 斤 | 1 | 1 | 0 | 0 |
| 桶 | 64 | 48 | 0 | 16 |
| 张 | 69 | 66 | 0 | 3 |
| 件 | 7 | 0 | 2 | 5 |
| 箱 | 1 | 0 | 0 | 1 |

→ **这些单位就是各商品自己的 `base_unit`**，不需要任何换算规则。
→ 唯一真实的换算缺口是 **`支→码` 213 行**（补 YPP 规格规则即可）。
→ `件` 的 2 行：`进口新闻纸/板装`（件→kg）、`编织袋/100个`（件→元，且 base_unit='元' 本身非法）→ 少量零头，人工处理即可。

### 7.3 `base_unit` 非法值
`元`(3) / `色`(1) / `床`(1) / `扎`(3) / 空(1) 共 9 行不是计量单位 → 过账时拦截并提示修正。

### 7.4 并发

## 九、验收标准

1. 建一张入库单 → 加明细 → **锁定** → 点「过账」→ 弹窗显示可入账行数与跳过原因 → 确认后 `/stock` 页对应仓库库存增加
2. **重复点过账** → 库存不变（幂等），按钮变「✓ 已过账」
3. 部分可过账的单 → 跳过行在弹窗和徽章里都能看到原因（「product 表无此商品」/「缺换算规则」/「基本单位非法」）
4. 点「冲销」→ 库存回退到过账前数值，流水表里正负两条都在，**过账记录不消失**
5. 补完 product 表后 → 再点过账 → 只补入之前跳过的行，已入账的不重复
6. `y` 单位的明细折算成「码」后入账，数量正确；`令`/`块`/`卷` 等单位直接 1:1 入账；`支` 走 `aux_unit`('1支=N码') 折算
7. 库存页能按仓库切换、分类筛选、搜索、导出 CSV
8. 库存页直接改数量 → 写 `adjust` 流水 → 刷新后数值仍在，且流水里能查到这次改动
9. **产品页选仓库 → 「库存」列显示该仓数量**；切仓即时变化
10. ⭐ **默认全部未启用 → 库存一律显示 0 且置灰**（`is_tracking=0`）
11. ⭐ **过账不改变启用状态** —— 入库过账后该商品仍显示 0，但流水已记、内部累计已加
12. ⭐ **盘点后生效** —— 填实际数 → 库存显示该数；若与内部累计有差额 → 有一条 `adjust` 流水记录差额
13. ⭐ **归零** —— 归零后库存显示 0，但状态是「已启用」（= 真 0），与「未启用」区分得开
14. ⭐ **冲销到 0 → `is_tracking` 仍为 1**（这是「真 0」）
15. ⭐ **不会重复计算** —— 未启用期间入库的货，盘点填的实际数已包含它，补过账也不会再加一次
16. M3 后 `PRAGMA table_info(product)` 里**没有** `stock_quantity` / `aux_quantity`，全库无 `no such column`
17. ⭐ **A3**：手工 `UPDATE` / `DELETE` / `INSERT OR REPLACE` / UPSERT `stock_ledger` 全被 `RAISE(ABORT)` 拦下，正常 `INSERT` 放行（3 个触发器都在）
18. ⭐ **A1**：`python tools/verify_stock_balance.py` 返回 0 差异；随机序列不变量测试通过；所有余额比较用容差 `1e-6`
19. ⭐ **A2**：过账事务中途人为抛异常 → 4 张表全回滚，无「流水已写、余额没更新」
20. ⭐ **A4**：补录上周入库单 → 流水 `occurred_at` = 上周日期（非今天）；期间汇总归到上周；无空值
21. ⭐ **A5**：盘点两种顺序提交结果一致；`as_of` 有值；期间流水在确认弹框逐笔可见
22. ⭐ **A6**：已过账订单点解锁 → **403「请先红字冲销」**

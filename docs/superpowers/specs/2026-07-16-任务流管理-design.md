## 1. 背景与目标

把现有"事后记账"的三套订单（出货/入库/装柜）之外，新增一条**贯穿式作业工单**，将
**装货 → 点数 → 送货 → 卸货**全流程串联管理，每个节点留证据（拍照）、可追溯，
并落到具体的"人 + 车"。这是 CLAUDE.md「长期规划」中"美团骑手式送货流程实时管控 + 证据链"的落地。

**本期采用独立系统（A 方案）**：先把任务流程端到端打通，**不改动**现有三套订单；
打通后再考虑把出货/入库/装柜嵌入（收编）进来（未来 M3）。

### 1.1 与管家婆辉煌版的边界（核心约束）

管家婆辉煌版是**现有核心系统**,负责:商品资料、库存账务、价格、客户/供应商主数据、应收应付。
本系统**只负责"出仓→卸货"全流程的可视化管控与证据链**,不重复管家婆的账务能力。

**与管家婆的衔接方式:无侵入 + 拍照/截图**——

**根因(2026-07-16 用户明确)**:管家婆辉煌版**没有数据接口**(无开放 API、无法直连数据库),且短期内**不会有**(用户口径)。这是架构选择的前提约束,不是"绕"。

- **不直连数据库**:管家婆的库封闭,直连不可行。
- **不调 API**:管家婆无开放 API,即便未来有也**建议不走**——避免紧耦合、方便任一方独立升级。
- **靠"图片 + 截图"作为数据载体**:**这是当前唯一可行的衔接方式**。
  - **入**:管家婆出"装车单/同价调拨单" → 操作员**手机拍照或截图** → 上传到本系统 → OCR 识别出 `source_order_no`、明细、客户、地址等。
  - **出**(本期不做,留 M3+):本系统的"已完成"任务,可一键生成"送货完成回执截图",反贴回管家婆作业务存证。

**结果**:
- 管家婆:账务核心,计数/价格/应收应付照旧
- 本系统:**作业流核心**,承接管家婆的"出仓"指令,一路管到"卸货签收"留证
- 两者**通过"图+号"解耦**——好处是任何一方改版都不影响对方,YAGNI 也成立

**未来(非本期)**:
- 管家婆有 API 时可考虑直连(本系统结构已留口子:`source_order_no` 即是跨系统对账键)
- 多点送货的子表 `task_destinations` 可对接管家婆的多送货点

## 4. 状态机

### 4.1 主线（含并行前置）

**7 个状态（6 推进 + 1 拒收终态，无回退、无 trip）**：

```
准备中 ──(指派司机 ‖ 打码 两项并行，都完成)──▶ 已装货 → 已点数 → 已到达 → 已卸货 → 已完成
                                                                          ↓ (整单退回)
                                                                       已拒收
```

> 精简说明：原"送货中"节点**取消**——司机点"装货完成"即**同时**标记出发（写 `depart_at`），到"已装货"状态已隐含"在途"。状态机省一档、司机少一次点击。`已拒收` 是**第 7 个状态**，整单退回时从 `已卸货` 旁路过去（见 §4.4），是终态、不再推进。

**关键：`准备中` 阶段有两条并行前置，装货前二者都必须完成：**
- **指派司机**：`driver_id` 已设置（调度/文员指派，或司机自建时自动带）。
- **打码**：`无需打码` 或 `打码完成`（见 §4.2）。

> `已装货` 的进入条件 = `driver_id IS NOT NULL` **且** (`coding_status='无需打码'` 或 `'打码完成'`)。
> 二者互不依赖、可任意先后完成；详情页用两个徽标显示各自就绪状态。

| 状态 | 触发动作 | 执行人 | 证据 |
|------|----------|--------|------|
| 准备中 | 建单 + 上传照片/截图 + OCR 识别明细（并行推进：指派司机 + 打码） | 司机/调度/文员 | 识别原图 |
| 已装货 | 两项前置完成后到场装车，点「装货完成」并**上传/拍照装车照**（=同时写 `depart_at`） | 司机 | ✅ 装车照（**传了才能进点数**）|
| 已点数 | 点数核对，上传点数照（规格标签照 / 整体照） | 文员/仓管 | ✅ 点数照（**传了才能进到达**）|
| 已到达 | 司机点「到达」（写 `arrive_at`） | 司机 | — |
| 已卸货 | 司机点「卸货」并**上传/拍照卸货照** | 司机 | ✅ 卸货照（**传了才能进完成**）|
| 已完成 | 上传客户签收单据 | 司机 | ✅ 签收单（**传了才算完成**）|

- **推进规则**：主线只能向前；**不提供主线回退**（纠错=新建退货/换货单，见 §4.4）。**唯一例外是司机退单**（`driver_release`），司机在 `准备中 / 已装货` 状态主动释放任务回 `准备中`（不是常规状态回退，而是"取消指派"语义）。
- **终态**：`已完成` = 正常送货签收、`已拒收` = 客户拒收（整单退回），二者均不可再推进。
- **证据硬闸门**（缺证据不能推进）：
  - `已装货 → 已点数`：必须已上传至少 1 张**装车照**（`stage=装车照`）。
  - `已点数 → 已到达`：必须已上传至少 1 张**点数照**（`stage∈{点数标签照, 点数整体照}`）。
  - `已到达 → 已卸货`：必须已上传至少 1 张**卸货照**（`stage=卸货照`）。
  - `已卸货 → 已完成`：必须已上传**客户签收单**（`stage=签收单`）。
- 每次推进写一条 `task_events`（谁 / 几点 / 从 X 到 Y / 备注）= 证据链骨架。

**司机退单（`driver_release`）**：司机在 `status ∈ {准备中, 已装货}` 时（即 `depart_at` 未写入前）可点击「退单」释放任务，清空 `driver_id` 与 `vehicle_id`，任务回到 `准备中`。**退单必须上传已装货物的照片**（`stage='退单照'`）留证，记 `task_events`（`event_type='driver_release'`）。**`coding_status` 保留不变**（若已 `打码完成` 不重置，师傅工不白费；`coder_id` 不动，让原师傅可继续照看）。一旦 `status` 进入 `已点数` 及之后（`depart_at` 已写入后实际意义是"在途"），不可退单。

### 4.2 打码支线（抢单模式，装货前闸门）

```
无需打码 → （备注无散码，自动判定）
待打码   → 进入抢单池，所有打码师傅可见可抢
打码中   → 被某师傅抢走并锁定，他人不可选
打码完成 → 该师傅执行完手动置位（+ 可拍打码照）
```

- **自动判定**：靠现有备注"散码"解析逻辑初始化 `待打码 / 无需打码`。
- **抢单**：打码师傅在 `/coding-pool` 看到所有 `待打码` + 自己 `打码中` 的任务，勾选抢单。
- **退回**：`打码中` 可点「释放」→ 回 `待打码`、清 `coder_id`，记 `task_events`。
- **闸门**：`待打码` 未变 `打码完成` 前，**禁止进入 `已装货`**；`无需打码` 无闸门。
- **重算限制**：一旦 `task.status` 进入 `已装货` 及之后，`coding_status` **不再自动重算**；明细编辑时若检测到散码变化但状态已超 `准备中`，前端提示"任务已装货，打码状态不可自动变更，请联系调度"。
- **与司机退单的耦合**：司机退单（`driver_release`）**不重置 `coding_status`**，已 `打码完成` 的保留（让重新指派后无需重打）；`coder_id` 不动（原师傅继续负责）。

### 4.3 并发防抢（工程要点）

抢单用**原子更新 + rowcount 判定**，非"先查后写"：

```sql
UPDATE tasks
   SET coder_id=?, coding_status='打码中', coding_claimed_at=?
 WHERE id=? AND coder_id IS NULL AND coding_status='待打码';
```

`rowcount == 1` 抢成功；并发时另一人 `rowcount == 0` → 提示"已被抢走"。

### 4.4 任务类型与纠错（无回退）

- **主线只进不退**：任务执行完（乃至任一环节）发现错误，**不回退主线**，而是**新建一张纠错任务**冲正，原单保留不动、作为证据。
- **`task_type` 业务类型**：
  - `送货`：默认，商品行数量为**正**。
  - `退货`：商品行数量为**负**（退回/冲减），`related_task_id` 指回被冲正的原单。
  - `换货`：**一张混合行单**——同一单内"退回旧货"记负数行、"换出新货"记正数行，一次送达一次搞定（Q21）。
- **退货/换货复用同一状态机**（准备中 → … → 已完成），仅语义与证据差异：

| 环节 | 送货 | 退货 | 换货 |
|------|------|------|------|
| 明细数量 | 正 | 负 | 混合（负行+正行）|
| 装货照闸门 | ✅ 必须 | ❌ **可免**（空车出库） | ✅ 必须（要装换出的新货）|
| **点数照闸门** | ✅ 必须 | ❌ **可免拍照** | ✅ 必须 |
| 卸货照闸门 | ✅ 必须 | ✅ **必须**（语义=装货：把退货装上车） | ✅ 必须（卸换出的新货+装退回来的旧货）|
| 签收单闸门 | ✅ 客户签收 | ✅ 仓库收货凭证 | ✅ 客户/仓库双方签收 |

**前端适配**：`task_type = '退货'` 时，按钮文字自动切换——"卸货"显示为"装货（退货）"、"装车照"显示为"装车照/退货装车"、"点数照"显示为"点数照（可免）"。状态机 6 态不变，仅 UI 文案按任务类型适配。

**整单退回（客户拒收，`return_create`）**：司机送货到达后客户拒收或无法送达（如客户未开门），司机点击「整单退回」按钮，**必须上传退货场景照片**（`stage='退货照'`）。系统**自动生成一张 `task_type='退货'` 的新任务**，关联原单 `related_task_id`，数量全为负，走退货流程。**原单进入 `已拒收` 终态**（与 `已完成` 并列，是第 7 个状态）——原单不需签收单，作为"曾被拒收"的证据保留。原单同时记一条 `task_events`（`event_type='return_create'`），新退货单记 `event_type='assign'` 由系统代写。

**任务作废（`task_cancel`）**：调度/文员可在 `status='准备中'` 时点击「作废」按钮，标记 `is_cancelled=1`。装货后不可作废。作废不走退货流程，不生成新任务，仅标记取消；作废任务从列表/抢单池隐藏，但仍可在数据库查询。作废记 `task_events`（`event_type='task_cancel'`）。

- **负数带来的连锁影响**：YPP 支数换算 / mismatch / 汇总统计需能正确处理负数量（实现时统一处理）。

## 5. 数据模型（6 张表）

```
staff
  id · name · gender · birth_date · role(单值: 司机/调度/搬运/打码/仓管)

  · vehicle_id→vehicles(司机常用关联车辆, 可空)

  id · task_no(系统编号, 格式 TD-YYYY-MM-DD-XXX) · source_order_no(单据订单号, UNIQUE 唯一约束)

  · source_type(装车单/同价调拨单) · customer
  · dest_address · dest_lat · dest_lng · dest_poi_name
  · status(主线状态) · coding_status(打码状态)
  · driver_id→staff · vehicle_id→vehicles · creator_id→staff · operator_id→staff

  · est_weight_kg · est_distance_km · depart_at · arrive_at

  · created_at · updated_at

task_items          -- 明细，照搬出货 5 字段（quantity 允许负数：退货为负）
  id · task_id→tasks · product_name · specification · quantity · unit · remark · sort_order
  · line_type(normal/return/exchange_out/exchange_in)  -- 显式标识业务含义，不依赖 quantity 正负推断

  · from_status · to_status(主线推进时用；非主线动作可空) · operator_id→staff · note · created_at
```

- 外键：`driver_id/creator_id/operator_id/coder_id → staff`，`vehicle_id → vehicles`，
  明细/图片/流水 `→ tasks`；`staff.vehicle_id → vehicles`。
- `unit` 沿用 `码 → y` 归一化三层防御（模型层 + API 层 + 前端 JS）。
- 图片存 `upload/YYYY-MM/`，DB 存相对路径，`/upload/<path>` 路由访问（同现有约定）。
- **`source_order_no` 唯一约束**：单据订单号肯定存在。OCR 识别出后先查重，已存在则拒绝创建并提示"该订单号已存在，点击查看已有任务"；**识别失败时允许手工输入/编辑**。唯一约束仅对非空值生效。
- **打码自动判定**：建单 OCR 后扫描所有明细 `task_items.remark` 是否含散码 → 初始化 `coding_status = 待打码 / 无需打码`；**明细被编辑后重算**（但已 `打码中 / 打码完成` 则不再变动）。
- **车辆自动带入**：指派司机时，从 `staff.vehicle_id` 自动带出该司机常用车填入 `tasks.vehicle_id`，可手工改；非必填、不作装货闸门。
- **明细冻结**：任务进入 `已点数` 后明细品项/数量冻结不可改（用状态天然锁，不单独做手动锁定）。

## 6. 身份与权限（B 轻量身份）

- **登录选择页（无密码）**：后期加一个登录选择页，进入系统先**选一个人**即可（暂不设密码）。选定后该人写入会话 = "当前操作人"，其 `role` 明确；所有操作记 `operator_id`。`staff.login_name/password_hash` 已预留，将来上密码登录不返工。
- **每个 `staff` 一个 `staff_code`**（免密令牌/链接），可用于将来发链接给司机免选登录。
- **权限强制（v1 即硬拦，不只是提示）**——校验全部收敛到 `can(operator, action, task)`：

| 动作 | 谁可以做（硬拦） |
|------|----------------|
| 建单 + OCR + 编辑明细 | 任意登录者（司机/调度/文员） |
| 指派司机（+带车辆） | 调度 / 文员 |
| 抢单 / 打码完成 / 释放 | **仅 `role=打码`** |
| 装货（含出发，Q23 合并）/ 到达 / 卸货 | **仅该任务 `driver_id` 本人** |
| 点数 | 仅 `role∈{文员, 仓管}` |
| 退单（`driver_release`） | 仅该任务 `driver_id` 本人，且 `status ∈ {准备中, 已装货}`（出发前）|
| 任务作废（`task_cancel`） | 调度 / 文员，且 `status = '准备中'`（装货后不可作废）|
| 整单退回（`return_create`） | 该任务 `driver_id` 本人，`status ∈ {已到达, 已卸货}`（客户拒收）|
| 主线状态回退 | ❌ **不提供**（纠错=新建退货/换货单，见 §4.4）|

- **建单页统一**：调度 / 司机 / 文员打开的**建单页面完全一致**，不因角色而变。区别只在建单人身份：
  - 司机自建 → 自动带 `driver_id=自己`，指派前置直接就绪。
  - 调度/文员自建 → `driver_id` 留空，进入待指派，由指派动作补上（并从司机带出常用车辆）。

### 6.1 为未来 RBAC 预留扩展（现在不建，纯新增升级）

现在权限判断很简单（按 `staff.role` 单值 + 上面几处硬编码校验）。为将来平滑升级到"多角色 + 细粒度权限控制"，遵循两条原则，保证将来是**纯新增表 / 加字段**，不改现有逻辑：

- **staff 表已预留** `login_name / password_hash` 两列（`is_active` 已在用，将来上账号登录时一起管），将来上账号登录直接填。
- **权限校验集中封装**：所有"谁能干什么"的判断收敛到一个 `can(operator, action, task)` 辅助函数里（第一版内部就是简单的 role 比对）。将来接 RBAC 时只改这一个函数的内部实现，调用点不动。
- **未来 RBAC 表草图**（M4+ 再建，本期不做）：
  ```
  roles            id · code · name
  permissions      id · code · name        -- 如 task.assign / coding.claim / task.advance
  role_permissions role_id · permission_id  -- 角色↔权限 多对多
  staff_roles      staff_id · role_id       -- 人↔角色 多对多（届时 staff.role 单值字段退役/迁移）
  ```
  届时 `staff.role` 单值字段迁移进 `staff_roles`，`can()` 改为查权限表，其余代码无感。

## 7. 界面

## 10. 测试 & 安全

- `tests/` 新增单元测试：
  - 状态机流转合法性（非法跳转被拒）
  - **装货两条并行前置**：仅指派未打码、或仅打码未指派时，禁止进入 `已装货`；两者都完成才放行
  - 打码闸门拦截（`待打码` 时禁止进入 `已装货`）
  - 抢单并发（两次原子抢单只有一次成功）
  - 抢单释放回池
  - **各环节证据闸门**：缺装车照/点数照/卸货照/签收单时，分别禁止推进到 点数/到达/卸货/完成
  - **装货=出发合并**：点装货完成时 `depart_at` 同步写入
  - **退货免装车照 + 免点数照**；**换货必拍所有照片**
  - **`source_order_no` 唯一**：重复订单号建单被拒
  - **抢单池权限**：非 `role=打码` 身份执行抢单/完成/释放被拒
  - 签收单据上传后才可 `已完成`
  - 备注散码解析（自动判 `待打码/无需打码`）
  - 单位 `码 → y` 归一化
  - **司机退单**：`准备中/已装货` 可退单，退单后 `driver_id/vehicle_id` 清空、`status` 回 `准备中`；装货后不可退单；退单必须上传 `退单照`；`coding_status` 保留 `打码完成` 不重置
  - **任务作废**：仅 `准备中` 可作废，作废后 `is_cancelled=1`，从列表/抢单池隐藏；装货后不可作废
  - **整单退回**：客户拒收 → 必传 `退货照` → 自动生成 `task_type='退货'` 新单、关联 `related_task_id`、数量全负 → 原单置 `已拒收` 终态（原单不需签收单）
  - **`coding_status` 重算限制**：`已装货` 后明细编辑不再自动重算打码状态
  - **`is_cancelled` 过滤**：作废任务从抢单池、列表默认视图中排除
  - **乐观锁**：`tasks.updated_at` 校验，同一任务并发编辑后提交者报错刷新
- **Schema 变更前按 CLAUDE.md 铁律**：先
  `Copy-Item worklog.db D:\BAK\worklog_<时间戳>.db` 完整备份；
  再跑建表迁移（`init_db()` 幂等加表，不碰旧表）。
